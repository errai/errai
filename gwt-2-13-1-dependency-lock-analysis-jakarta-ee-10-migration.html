GWT 2.13.1 Dependency Lock Analysis

Pre-migration assessment for JavaEE → Jakarta EE 10 · Errai 4.19.0-SNAPSHOT

Key finding: GWT 2.13.1's gwt-user JAR hard-codes javax.validation:validation-api:1.0.0.GA as a compile dependency and bundles the super-source classes under the javax.validation.* namespace inside the JAR. This creates the deepest lock in the whole graph — the GWT Validation module cannot be migrated to jakarta.validation without either patching GWT or forking the errai-validation GWT module.

1. Lock Legend

BadgeMeaning
HARD LOCKCannot be changed without replacing or patching the GWT runtime itself. Blocked for Jakarta EE 10.
SOFT LOCKVersion is constrained by a transitive dependency that is itself upgradeable in isolation — needs a coordinated upgrade.
UPGRADEABLENo GWT constraint; can be upgraded to the Jakarta EE 10 equivalents.
PARTIALSplit artifact: server-side code can be migrated, GWT client-side portion stays on javax.*.

2. Dependency-by-Dependency Analysis

2a. Hard Locked — Cannot Migrate to Jakarta EE 10

Dependency Current Reason for Lock Status
javax.validation:validation-api 1.0.0.GA gwt-user-2.13.1.jar declares a compile dependency on javax.validation:validation-api:1.0.0.GA. The JAR also bundles GWT super-source files under javax/validation/super/ and a javax/validation/Validation.gwt.xml module descriptor. The GWT Validation rebind framework (com.google.gwt.validation.* inside gwt-user) generates validators that reference javax.validation.* types at compile time. Moving to jakarta.validation is impossible without GWT itself shipping a jakarta.validation super-source. HARD LOCK
javax.servlet:javax.servlet-api 3.1.0 gwt-user-2.13.1.jar declares a compile dependency on javax.servlet:javax.servlet-api:3.1.0. gwt-dev-2.13.1.jar similarly lists Jetty 9.x in its BOM (jetty.version=9.4.58.v20250814) and Jetty 9 is a javax.servlet container. The GWT embedded DevMode server and codeserver run inside Jetty 9. Migrating the Errai server-side servlets to jakarta.servlet breaks the GWT DevMode classpath. HARD LOCK
javax.validation:validation-api (sources classifier) 1.0.0.GA gwt-user also pulls the -sources classifier of the same 1.0.0.GA validation-api because GWT compiles .java sources for the client-side validator generation. Both the binary and sources classifier must stay at 1.0.0.GA. HARD LOCK
org.eclipse.jetty:jetty-* (all 9.4.x) 9.4.44.v20210927 GWT 2.13.1 BOM pins Jetty to 9.4.58.v20250814. Jetty 9 is the last series on javax.servlet. Errai currently overrides Jetty to 9.4.44, but it cannot jump to Jetty 10+ (jakarta.servlet) while staying on GWT 2.13.1's DevMode and codeserver, which depend on Jetty 9 internally. jetty-continuation was removed in Jetty 10. HARD LOCK
org.glassfish:javax.el 3.0.0 This is the EL 3.0 implementation under the javax.el namespace. Used at runtime during DevMode and tests via the Weld servlet integration. Weld 3.x (which is locked — see §2b) expects javax.el / EL 3. Moving to EL 5 (jakarta.el) requires Weld 5+. HARD LOCK

2d. Server-Side Source Migration — Partial (server vs. client split)

Dependency / Usage Situation Status
javax.enterprise.cdi-api imports in server classes Server-side .java files under src/main/java that import javax.enterprise.*, javax.inject.* can be renamed to jakarta.*. GWT client-side code that goes through the GWT compiler must keep javax.* because the CDI super-source stubs in errai-javax-enterprise are under the javax namespace. PARTIAL
errai-javax-enterprise GWT super-source module This module provides client-side stubs for CDI annotations (@ApplicationScoped, @Inject, etc.) under the javax.* namespace. GWT code generation in errai-ioc, errai-cdi-client etc. reference these as javax.*. These cannot be renamed to jakarta.* until GWT ships native jakarta.enterprise/inject support. HARD LOCK
javax→jakarta rename in server servlet code Errai bus servlets, CDI server extension, bus-websocket server endpoint, and all non-GWT-compiled server code can have imports renamed. However, running those in a DevMode context still goes through GWT's embedded Jetty 9 (javax.servlet), so a dual-path or server-only deployment mode is needed. PARTIAL

3. Cascade Upgrade Summary

To fully reach Jakarta EE 10 the following coordinated upgrades are required as a group — they cannot be done independently:
  • Weld 3.1 → Weld 5.x — unlocks CDI 4.0 (jakarta.enterprise), Interceptors 2.1, EL 5
  • Hibernate ORM 5.3 → Hibernate ORM 6.x — unlocks jakarta.persistence 3.1 (JPA 3.1)
  • RESTEasy 3.11 → RESTEasy 6.x — unlocks jakarta.ws.rs 3.1 (JAX-RS 3.1)
  • DeltaSpike 1.9 → DeltaSpike 2.x — follows Weld 5 / CDI 4
  • Jetty 9.4 → Jetty 11.x — unlocks jakarta.servlet 6.0 (Servlet 6)

4. Items That Stay on javax.* Permanently (GWT 2.13.1)

The following items cannot be migrated as long as GWT 2.13.1 is the compiler and runtime. They require either a future GWT release with native Jakarta EE support, or maintaining a dual javax/jakarta compatibility shim:
  • javax.validation:validation-api:1.0.0.GA — bundled super-source in gwt-user JAR, used by GWT validator code generation
  • javax.validation:validation-api:1.0.0.GA:sources — sources classifier required by GWT rebind
  • javax.servlet:javax.servlet-api:3.1.0 — compile dependency of gwt-user; Jetty 9 (gwt-dev) is javax.servlet
  • errai-javax-enterprise GWT super-source stubs — all CDI/inject annotations used on the client side
  • org.eclipse.jetty:*:9.4.x — embedded in GWT DevMode codeserver
  • org.glassfish:javax.el:3.0.0 — EL 3.0 impl for javax namespace, matched to Weld 3.x + Jetty 9
  • org.hibernate:hibernate-validator:4.1.0.Final — implements BV 1.0 (javax.validation), locked to gwt-user's BV 1.0 dependency
